# femaktiv live chat

## Goal of the document

Define conversational assistance using private chat context, anonymous model processing and cited evidence.

## Scope

This contract extends the [bilingual platform](platform.md) with an explicitly configured live mode for a private prototype using fictional information. The initial acceptance scenarios are nutrition with hypertension, protein/fibre goals and dietary exclusions, and organising support for an older parent after an injury in Germany. General conversation remains available. Public examples keep their approved wording; live-state controls are authorised by the live-chat implementation request. This contract supersedes the platform's placeholder-only reply behavior when live mode is selected. It does not activate the historical recipe-catalogue or clinical-review gates of the initial nutrition build.

The user's subsequent instruction removes Brave Search and the local-contact lookup feature, including its credential requirement and locality control. There MUST NOT be a replacement search provider, fabricated contact results or simulated search. Anymize remains the only runtime external service. Model web search MUST NOT be claimed or enabled by guessing API parameters; it requires documented support through the anonymous endpoint and verification of returned sources.

## Modes and configuration

`FEMAKTIV_AI_MODE` MUST be `placeholder` (default) or `live`. Live requests require server-only `ANYMIZE_API_KEY`, `ANYMIZE_MODEL`, `ANYMIZE_ZDR_CONFIRMED=1`, and `ANYMIZE_FALLBACKS_DISABLED_CONFIRMED=1`. The last two settings record the operator's confirmation that account-level Zero Data Retention is enabled and provider-side fallback models are disabled; they MUST NOT be described as remotely verified or change the provider account. Missing configuration MUST produce an explicit unavailable state, without unprotected provider or fixture fallback. Existing stored modes MUST remain unchanged.

The application MUST explain that selected text reaches its server and Anymize, that masking happens before the downstream model, and that useful health details remain sensitive. Neither provider metadata nor identifier replacement establishes complete anonymity or clinical correctness. Logs MUST exclude private content, raw provider exceptions, credentials and mappings.

Live access MUST require `User.live_chat_enabled`, disabled by default for both new and existing accounts and editable only through operator-controlled administration. Staff status alone MUST NOT grant live access. Check current approval before accepting a new paid turn and before further external stages. Public registration follows the platform's default-closed policy.

The intended masking policy covers personal names, street addresses, email/phone details, exact birth dates, financial and identity numbers, and legal case/contract identifiers. Prefer relationships and roles in answers; never depend on restoring personal identifiers. Retain relevant health conditions, allergies versus preferences, practical constraints, care needs, and meaningful relative dates/deadlines. Exact dates and legal facts can remain sensitive; transmitting them MUST be limited to the selected context. Do not invent provider category controls or represent a prompt as enforcement of the provider's redaction.

## Conversation and active context

The assistant SHOULD answer naturally and ask at most three questions when missing or ambiguous facts materially affect the answer. It MUST distinguish reported facts from assumptions, preferences from allergies, and information about the user from information about a parent. It MUST NOT infer absence of allergies from missing information. General guidance and practical next steps MAY accompany clarification. Mentioning a diagnosis alone MUST NOT cause an automatic refusal. The assistant MUST NOT invent diagnoses, treatment changes, supplement prescriptions or service eligibility.

Live chat MUST use an isolated context segment. The first live request in an existing chat MUST exclude its earlier placeholder conversation. Raw messages and active note copies within the current segment are available to intake. Account identifiers, other chats and unrelated notes MUST NOT be included. Bound the input to 60,000 characters; exceeding the bound MUST request a context reset or smaller note selection rather than silently discarding constraints. No rolling model summary is retained in this version.

Selecting notes on a live message pins immutable title/body copies in that chat, with at most five active notes in total. Later replies MUST reuse those copies. Editing or deleting the original MUST NOT silently update or remove a pinned copy. Per-message context snapshots MUST include the copies actually used. Owners can explicitly remove, refresh or clear active context. Remove/refresh/reset MUST begin a new segment, invalidate any in-flight reply, and exclude all earlier messages and derived content from future calls. Earlier messages remain visible. New chats MUST start without inherited context.

The application MUST NOT request a city or postcode for a removed search feature. Legacy saved locality values MUST NOT enter active context or model input. The retired locality context action MUST be rejected. Existing database fields MAY remain for migration compatibility without exposing them as an active capability.

## Provider and retrieval

Use `POST https://app.anymize.ai/api/v1/llm-anonymous/chat/completions`, with `stream=false`, the requested English/German language and JSON-schema output. An adapter MUST check `_anymize.anonymized` is exactly true, successful completion, bounded response size and the application schema. Do not request identity mappings or depend on de-anonymization. The configured model MUST be an actual account-accessible identifier; the explicit evaluation command checks it with `GET /api/v1/llm/models`. Model/schema support and preservation of useful facts require live evaluation.

One turn performs structured intake, then either returns relevant clarification or selects passages from the local evidence library and composes a cited answer. It MUST make at most two model calls within a 60-second application deadline. The local server timeout MUST accommodate that deadline. There are no automatic paid retries, tool-execution loops, public-page requests or streaming replies.

Content-free accounting MUST survive deletion of chats, messages, notes and their copies. Default limits are 30 accepted reservations per account over the preceding hour (`FEMAKTIV_LIVE_USER_HOURLY_LIMIT`) and 100 across the application per UTC calendar day (`FEMAKTIV_LIVE_DAILY_LIMIT`). Positive integer overrides MAY tune these prototype limits. These are request allowances, not a currency budget. Check and reserve both limits atomically before external work, including concurrent requests across chats/accounts. Accepted reservations count even if provider work fails; duplicates reuse the existing reservation without another charge. Permit only one unexpired, unfinished reservation per account. The lease MUST survive chat deletion until its worker finishes or its deadline expires, preventing deletion from freeing concurrent paid work. Migration MUST preserve existing reservation usage. No transcript, note body, name, address or provider credential belongs in accounting records.

The evidence library MUST contain versioned, source-checked paraphrases with stable ids, titles, organisations, exact HTTPS URLs, sections, nullable publication/update dates, checked dates, topic tags, population applicability and limitations. Source checks MUST be distinguished from human editorial approval and clinical review. Begin with DGE general food guidance, NHLBI DASH guidance, German federal discharge/care guidance and ZQP. Targeted NIH/EFSA entries MAY support nutrient questions; bulk cohort ingestion and model training are outside this change.

Care questions MUST remain answerable with supplied evidence, practical planning and call preparation. The model MUST NOT claim to have searched the web or verified current contacts, invent local contact details, or ask for locality to run a search. Existing evidence-library directory links MAY be cited as directories; they MUST NOT be presented as fetched local results. Availability, language support and eligibility MUST NOT be invented.

Supplied content MUST remain untrusted input. Provider requests MUST use the fixed Anymize endpoints, validate public destinations and pin connections to validated public IP addresses. Response sizes and elapsed time MUST be bounded. The model MUST NOT choose arbitrary fetch URLs or follow instructions embedded in source passages.

Each answer paragraph MUST identify only supplied source ids. The server resolves URLs, validates ids and stores citation snapshots with the reply. Source names and URLs MUST come from source records rather than generated prose. Nutrition/care factual explanations require citations; practical suggestions and questions are distinguished from factual explanations. Source-backed prose is still subject to semantic evaluation and MUST NOT be represented as automatically proven correct. Historical saved citations remain readable; new replies MUST NOT generate contact cards.

## HTTP and persistence

The existing message POST retains exactly `content`, `note_ids` and `client_request_id` with the platform's limits. Placeholder behavior remains atomic and offline. Live note ids add new pinned copies; an existing pinned note requires an explicit refresh to replace its copy. The live response adds `kind`, `paragraphs`, `citations`, `lookup_status`, `active_context` and `status`; `mode` reflects the stored reply.

`lookup_status` remains a compatibility field for saved messages. New replies MUST use `not_requested`; historical values MUST NOT be rewritten or interpreted as a current lookup.

`GET /<language>/api/chats/<chat_id>/turns/<client_request_id>/` returns the owner's stored completed result, a 202 processing response, or a stored error. `POST /<language>/api/chats/<chat_id>/context/` accepts one action: `remove`/`refresh` with `note_id`, or `reset` without another property. It returns the current context. All private access MUST enforce ownership, CSRF on writes and no-store caching.

Before network activity, atomically create a durable request reservation, fingerprint the submission and capture its context. Database uniqueness MUST permit only one processing turn per chat. External calls MUST run outside database transactions. Recheck the reservation before each external stage and after intake; an invalidated/deleted turn MUST NOT proceed to later composition. An already transmitted request cannot be recalled. A repeated id with the same payload MUST reuse its reservation/result without another call; changed payload returns 409. Another request during processing returns 409. Completion MUST atomically save both messages and snapshots only if the reservation and context are still current. Deleting a chat MUST prevent late completion from recreating it.

Failed or expired reservations retain safe error metadata and the payload fingerprint, not private working copies. Unknown outcomes MUST NOT be retried automatically. The UI MUST retain a failed draft, poll a processing reservation, and offer an explicit new attempt after a terminal failure; a lost response first retries the same id. Context resets and navigation MUST suppress stale results. The browser MUST stop waiting after 75 seconds while retaining the recovery id and draft. Context updates have a 15-second browser deadline; if a write outcome cannot be confirmed, refresh the context before permitting further inference.

## Verification and operation

The [live-chat workflow](../../workflows/implement-live-chat.donna.md) owns implementation and offline verification. Routine checks MUST disable external traffic even when the process inherits real credentials. Unit tests MUST cover Anymize-only configuration, provider schemas/metadata/errors, network destination protections, citation integrity, care guidance without search, bounded context, owner isolation, reservations, timeouts and context invalidation. Mocked multi-turn scenarios and browser checks MUST cover both languages and 390px/1440px.

`manage.py evaluate_live_chat --allow-provider-calls` is a separately invoked fictional evaluation. It MUST verify configuration/model access, structured output, anonymization metadata, meaningful intake facts and cited scenario results, and report safe measurements plus the fictional generated answers for human review. It MUST NOT run from ordinary checks or claim anonymization accuracy from metadata alone. Implementation can be complete with live evaluation explicitly unperformed.

Provide fixed fictional English/German masking cases covering the declared identifier categories and useful facts. An optional local evaluator MUST inspect actual anonymizer output supplied for those cases, detect remaining known identifiers and missing essential facts, and retain the fictional masked text for human review. Identify operator-supplied export provenance; do not claim independently attested origin or equate an LLM echo/final answer with the input seen by that LLM. The combined anonymous-chat API does not document a masked-input inspection response under account ZDR. Do not disable production ZDR to obtain an export or invent an endpoint. Missing export evidence MUST leave masking evaluation explicitly untested, with model integration results reported separately. This developer inspection MUST NOT become a normal-chat step or setup prerequisite; an integration-only check MAY pass while clearly reporting masking as untested. Routine tests mock external services or use fictional exported-text fixtures.
